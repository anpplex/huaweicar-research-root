## 三、已验证的关键事实

### 3.1 纯 shell 能做什么
1. 写 sched/vmscan 事件、tracing_on、trace_clock，读 trace/trace_pipe_raw
2. 抓 `sched_process_exit`，用 trace_clock=mono 与用户态 CLOCK_MONOTONIC 同源比对
3. 窗口不是 92µs：子进程 exit_itimers 后变 zombie，**不 reap 就能无限拉长**（实测喷洒期间事件已过、reap 推迟 20.8ms）
4. 高内存压力下 exit 事件会迟到 19.7~36.7ms
5. **/dev/hvgr0 O_RDWR 可开**（Kirin GPU，与白鹿 kgsl-3d0 对位）

### 3.2 已判死（勿重复）

## 四、当前唯一活路（下一步入口）

**/dev/hvgr0**（Kirin GPU，0666）是白鹿"kgsl 物理读写 → PHYSCAN 找 STEXT"思路在本机的唯一对位面。

已知：
- 驱动设备：`dc000000.hvgr`（/sys/class/misc/hvgr0/device）
- sysfs 的 dev/uevent 对 shell 不可读（Permission denied）
- 驱动源码**不在** kernel-src（kernel/drivers/gpu 只有 arm/drm/gmc/host1x/ipu-v3/vga；vendor/open_source 无 GPU）
- 用户态库：/vendor/lib64/libGLES_v210.so、libgpucl.so、libbishenggpucompiler_v210.so

下一步要做的（未开始）：
1. 拉 libGLES_v210.so 逆向 `ioctl(fd, cmd, arg)` 的 cmd 表与结构体
2. 找 hvgr 的 GPU 内存分配/映射接口，判断是否暴露 GPU VA↔PA
3. 找可越界/可复用的 ioctl 参数（漏洞点）
4. 若拿到物理读写 → 复刻 PHYSCAN（16MB 步长扫 STEXT）→ kbase → slide

### 验证结论
1. 五个探针在当前设备状态下 100% 可跑通，无崩溃、无残留（内存已释放，memfree 回到 1.12GB）。
2. 纯 shell 侧唯一稳定可用的是 **sched_process_exit + 时钟对齐 + 窗口拉长**。
3. vmscan/reclaim 信号依旧为 0，不能作为 GATE 信号。
4. GPU 节点 /dev/hvgr0 O_RDWR 稳定可开，是唯一未被否定的新入口。
