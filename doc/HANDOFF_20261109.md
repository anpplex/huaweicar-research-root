## 0. 一句话现状

纯 shell（不依赖 relay）的 CVE-2026-98260 利用链已经能**稳定建洞、稳定打中窗口、并真正执行到 rb_erase 写原语**；
唯一卡点是「631 个 posix timer 中，被 arm 的那个落在 slab 的哪个对象槽」无法用 filemap 通道确定，
导致模板几何（`arm_i=29 → off=0xF58`）是猜的，落刀即野指针 panic。

## 2. 硬约束（用 8 次重启换来的，务必遵守）

1. **绝不 SIGKILL 任何带 timer 的进程**（wr93x / victim / 其子进程）。reap 会走 `release_task → posix_cpu_timers_exit`，脏 timer 链直接 panic。
2. **不要用 `timeout|head` 读 `trace_pipe_raw`**（`kaslr_self.sh` 老做法）：被杀的阻塞进程同样触发上述 UAF。
3. **一个 boot 只跑一次 wr93x**。反复跑会把 `posix_timers_cache` 从 6 个 slab 涨到 37+，撞上代码里的 `slabdata > 33` 硬闸，全部弃用。
4. **不要激活 relay**（`am instrument com.root.adbinvoke/InvokeRoot`）——多次崩溃都发生在它之后 20~40 分钟的延迟窗口。
5. 执行完不 kill、不 reboot；需要重启必须用户批准。

## 3. KASLR slide（已验证的正确做法）

- 工具：设备端 `/data/local/tmp/skslide2`（`irq/tasklet_entry` + 3 个 CPU + 0.5MB 上限 + 4 字节步进匹配 `kallsyms_new.txt` 入口）。
- **每 boot 必须重算**，要求两次运行结果完全一致才算有效。
- 本机特征：`slide ≡ 0x80000 (mod 0x200000)`，粒度 64KB。历史值：
  `0x1B08A80000`、`0x1F69A80000`、`0x28BA280000`、`0x23FAC80000`、`0x23DDC80000`、`0x14F2280000`、`0x16E2E80000`、`0x1E03E80000`。
- **不要用崩溃 PC 反推 slide**：本机 blackbox 打印的是归一化（未滑动）地址，`pc=0xffffffc010122acc` 恒等于静态地址。之前"slide 偏 0x1480000 / 粒度 64KB"的结论是跨 boot 混比造成的误判，已撤回。
- 已确认 `kallsyms_new.txt` 无 0x80000 偏移（`kaslr_self.sh` 注释里的旧说法作废）。

## 4. 崩溃取证（不需要 relay）

```
adb shell 'cat /sys/fs/pstore/console-ramoops-0 > /data/local/tmp/pc.txt'
adb shell 'cat /sys/fs/pstore/dmesg-ramoops-0 > /data/local/tmp/dm.txt'
```
`/sys/fs/pstore` 目录列表会 EACCES，但**直接 cat 具体文件可读**（shell 可读）。

已知唯一签名：
```
pc : release_task+0x2a4/0x12ec   lr : release_task+0x124
x27: dead000000000122 (LIST_POISON2)   WnR=0 野指针读
Kernel panic - not syncing: Oops: Fatal exception
```
- 早期崩在 `init`（kill 掉孤儿/被 timeout 杀的进程）；
- **现在崩在 `wr93x` 自己**（`waitpid(victim)` 的 release_task）——这本身就是"写原语已执行"的证据。

## 5. 纯 shell 通道（filemap）实现要点

- 事件：`mm_filemap_add_to_page_cache` / `mm_filemap_delete_from_page_cache`，shell 可 enable，输出明文 `page=<hash> pfn=<dec>`。
- 建洞：写 filler 4096 页 fsync 后整文件 `posix_fadvise(DONTNEED)` 灌满 pcp；再逐对释放空洞页（必须物理相邻 pfn 偶+pfn+1 同文件）。
- 模板：`ps_make_holes` 在 **fadvise 之前**把假 rb_node 写进每个空洞页（`ps_grid`：每 0x110 一槽，`parent=(misc-8)|1, right=Pnode, left=0`；公共桥页额外 `build_ins_tmpl(0xF58)`）。
- 关键常量：`PAGE_OFFSET=0xffffff8000000000`，`MISC_LIST_OFF=0xffffffc0135c7860`，`posix_timers_cache` 对象 0x110、30 对象/order-1 slab、`node=+0x88` → 对象 29 的 node 在 8KB 块头页 **0xF58**。
- 公共桥页保证「不管命中哪一对，rb_right 都指向同一个 Pnode」，避免桥地址不确定。

## 7. 代码现状（本轮改动）

1. **快速路径已恢复**：puresh 也 fork reader + killer，走 `kill → waitpid → ins_bridge → cred` 原链路，只把 hole/gate 换成 filemap。`PSNOKILL=1` 可跳过 killer（仅诊断用；该模式注定 MISS）。
2. `ps_gate_run()`（约 L1793）改为**精确占用识别**：喷涂后扫 add 事件，找出"没被抢回"的空洞对，打印 `[PS] 被占用 pair[i] pfn=...`；要求 `nocc == 1` 才放行，并据此设置
   `g_node_pfn = occH; g_node_va = PAGE_OFFSET + occH*4096 + 0xF58;`
3. `PSHOLD=1` 探针（约 L5511）插在父进程发 `go` 之前，想"arm 完→测量→再落刀"。**当前实现有 bug**：它读的 `g_wfd` 4 字节通道已被父进程 `xread(g_wfd,&okc,4)` 消费，只能 2s 超时跳过。修法：给 `ai` 单独开一条 pipe（或改消息格式为 `[ok][ai]` 定长 8 字节）。
4. 模板低两位：`parent=(misc-8)|1` 表示 black。若 rb_erase 命中我们的节点，会进入 rebalance 分支而非 Case1，**这也是崩溃的另一嫌疑**，需要与"槽位不对"一起排除。

## 8. 待解决的核心问题

**arm 的那颗 timer 在哪个 slab / 哪个槽？**
- filemap 通道能给到"页 pfn"，给不到"页内对象序号"；
- 代码用 `arm_i=29`（"首个满 slab 的最后创建对象"）是推测，从未验证；
- 27 个 slab 里挑错一个 → rb_erase 读野指针 → panic。

## 9. 三条可选路径

| 方案 | 内容 | 代价 |
|---|---|---|
| A | 纯 shell + 槽位轮询：每次 boot 只试一个对象序号（0..29），命中即停 | 最多 30 次重启，完全不碰 relay |
| B | 只让 relay 开 `kmem_cache_alloc` 一个事件，拿精确对象地址；其余仍直写 | 用一次 relay，风险已知 |
| C | 修 `PSHOLD` 握手（`ai` 单独 pipe）+ 修正 black/red 位，先验证页占用，再落刀 | 一次代码改动 + 多次 boot |

推荐 C → A：先把页级占用与颜色位验证对，再用轮询补槽位。
